# system architecture and design

the ebram (email bug report automation machine) system works by using Cloudflare email forward workers with a node orchestrator to enable agentic workflows from both message inputs from both contact forms and direct email triggers. the output of an ebram workflow is usually downstream email messages to relevant humans or further automations like updates in systems of records.

the email forward worker (efw) is responsible for handling both direct email sends e.g. ebram@software.co and http handler that backs a contact form or any internal workflow form.

the ebram system is design to be generic and flexible to any kind of workflow automation that starts from a direct email or form submission.

the efw layer handles spam messages using a 2 layer gate, the first is a generic keyword based heuristic, and an optional 2nd layer can be enabled using LLM based deep spam classification with a economical model like Deepseek-V4-Flash using Cloudflare's Workers AI bindings. spam messages are dropped before getting any further into the orchestration layer.

messsages that get past the spam gates proceed to either get forward to the configured contact email or get forwarded to an agentic orchestrator if certain keywords match. the primary usecase for now is bug triage and investigation for some designated project repo on Github. the orchestrator is backed by Cursor Cloud SDK, but can also use other code harnesses which is WIP and will be added later.

if eligible for bug report triage (the only workflow currently implemented), the efw will forward to an Node agent orchestrator service that is separately deployed (e.g. railway), the orchestrator accepts and returns right away so the email worker does not need to wait for the results. there is a `requestId` that is generated by the efw that gets passed to the orchestrator so that an entire email request flow can be tracked across the entire workflow. the orchestrator also handles rate limiting per ip address and is protected via a shared access key with the email worker.

orchestrator bug triage: the only workflow supported at the moment is bug triage. bug triages work on a specific Github repo managed by Cursor cloud agents. the orchestrator handles different scenarios such as out of scope, not valid, and further spam checks. it also handlers unsafe prompt injections with a JIT generated nonce token. only message requests that are deemed as valid are allowed to be sent to the agent harness to be process. this is important because the agent has access to sensitive documents and the actual code files that might be private to the org. this extra gate also protects against misuse and wasted tokens. the output of the triage agent creates a structure json object with specific fields like verdict, title, summary, affectedPaths, proposedFix, effort, and risks that we care about which gets fed into the final output of the bug triage run is a notification that gets sent to designated developer email and a Github issue opened. the email service uses resend.dev as the default. Github tokens are required for issue read/writes.

the ability to add and remove agentic workflow tasks as configuration is a core design choice. we included a `ebram.config.yaml` file for ease of configuration. a deployment should be able to customise their email workflow agent to do exactly what they want without too much core code modifications.

this major future development effort would be to replace Cursor with a custom open agent harness based on Pi or Deepseek Harness that can run on any server and run open models from providers like DeepInfra or Fireworks.
